# grain-guard — задачи MVP

**Цель MVP:** доказать на одном объекте, что система предупреждает о самосогревании
зерна раньше оператора и предотвращает измеримый ущерб (тонны / рубли).

- Основной горизонт прогноза: **72 часа**
- Скоуп: синтетические данные + физическая модель + простой ML (без deep learning) + один пилотный элеватор
- Вне скоупа MVP: deep learning, realtime-стриминг, мобильные приложения, интеграция с АСУ ТП элеватора

**Общее Definition of Done (применимо к каждому этапу):**

- `uv run pytest` — все тесты зелёные
- `uv run ruff check .` — без замечаний
- параметры и допущения задокументированы (docstrings / `docs/`)
- результат этапа воспроизводим одной командой, указанной в этапе

Легенда приоритетов: `[P0]` — блокирует следующий этап, `[P1]` — важно, `[P2]` — можно отложить.

> Статусы обновлены 2026-10-07 по итогам приёмки (синтетика n=1000, seed=42, VPS).
> «(частично: …)» — начато, критерий не закрыт. Источники параметров: `docs/sources.md`.

## Этап 1. Синтетические данные

**Цель:** физически правдоподобный датасет для разработки и отладки моделей до получения реальных данных.

Задачи:

- [x] `[P0]` 1.1. Описать схему записи: `silo_id, timestamp, T_zerna_1..6 (слои датчиков), W_vlazhnost, T_vozduha, tip_zerna, data_zagruzki, srok_hraneniya_dney` (storage_day; incident_id нет)
- [x] `[P0]` 1.2. Генератор «нормальных» траекторий: сезонный ход T воздуха, суточные колебания, тепловая инерция зерновой массы, шум датчиков
- [x] `[P0]` 1.3. Генератор инцидентов: локальный очаг самосогревания (Q10-кинетика дыхания зерна, рост влажности в очаге), случайные время начала, слой и скорость развития (партии — только вне безопасной зоны CGC, docs/sources.md п. 1.1)
- [x] `[P0]` 1.4. Разметка таргета: `incident_start`, `incident_detected_by_operator` (момент превышения фиксированного порога T 32 °C), `incident_id` (частично: нет отдельного id)
- [x] `[P1]` 1.5. CLI: `uv run grain-guard synth --n 1000 --seed 42 --out data/synthetic/`

Критерии приёмки:

- [x] Генерируется ≥ 1000 траекторий силосов, 3 типа зерна (пшеница, ячмень, кукуруза), шаг 1 час, длительность 60–120 суток
- [x] Доля траекторий с инцидентами 30–40% (0.35); время начала инцидента распределено по всему сроку хранения (10–91 %)
- [x] Физическая валидность: T зерна в пределах −5…+60 °C, влажность 9–25 %, в очаге T монотонно растёт быстрее фона (частично: ≥1 °C/сутки в 55 % инцидентов; остальные — медленные очаги у едва влажных партий)
- [x] Воспроизводимость: одинаковый `--seed` даёт бит-в-бит одинаковый датасет (юнит-тест)
- [x] Юнит-тесты на схему данных: нет пропусков timestamp, нет NaN вне спецификации, все silo_id уникальны

## Этап 2. Физическая модель (baseline № 1)

**Цель:** детектор на основе теплового баланса и критических кривых — без обучения, как основа для сравнения и санити-чек синтетики.

Задачи:

- [x] `[P0]` 2.1. Модель тепловыделения: дыхание зерна как функция T и W (Q10-кинетика), теплопроводность зерновой массы, теплообмен с воздухом (+ AST-модель порчи ASABE D535)
- [x] `[P0]` 2.2. Критические кривые «T ↔ W» по типу зерна (по справочным данным хранения, источники — в `docs/`) — CGC Safe Storage + ASABE D535, см. `docs/sources.md`
- [x] `[P0]` 2.3. Правило тревоги: прогнозная T превышает критическую кривую в горизонте ≤ 72 ч → alert(level, eta) (частично: флаг alert есть, level/eta нет)
- [ ] `[P1]` 2.4. Отчёт: калибровка параметров на синтетике, границы применимости

Критерии приёмки:

- [ ] На синтетике: recall по инцидентам ≥ 0.9 (сейчас 0.81), средний lead time до `incident_detected_by_operator` ≥ 24 ч (141 ч ✓)
- [x] Ложные срабатывания ≤ 2 на силосо-месяц на синтетике без инцидентов (0.24)
- [ ] Юнит-тесты: энергобаланс сходится (расхождение < 1 %), граничные случаи (T воздуха ниже T зерна, W ниже минимума хранения)
- [x] Каждый параметр модели имеет ссылку на источник или пометку «подобрано на синтетике» (`docs/sources.md`)

## Этап 3. Фичи и ML-модель (baseline № 2)

**Цель:** простая обучаемая модель, которая превосходит физическую по lead time или точности.

Задачи:

- [x] `[P0]` 3.1. Фичи: dT/dt за 6/12/24/48 ч по каждому слою, разница слоёв (градиент), скользящие средние/дисперсии, влажность, T воздуха, тип зерна, срок хранения
- [ ] `[P0]` 3.2. Таргет: инцидент начнётся в течение 72 ч (бинарный) + регрессионная оценка времени до инцидента (частично: бинарный есть, регрессии нет)
- [x] `[P0]` 3.3. Валидация без утечек: сплит по `silo_id` + time-based split внутри траекторий (+ автотест на утечку)
- [x] `[P0]` 3.4. Модели: LogisticRegression и HistGradientBoosting; выбор по отложенной выборке; калибровка вероятностей (CalibratedClassifierCV)
- [ ] `[P1]` 3.5. Отчёт feature importance + анализ ошибок (частично: importance есть, анализ FP/FN нет)

Критерии приёмки:

- [x] ROC-AUC ≥ 0.85 на отложенной выборке (72 ч горизонт) — 0.94
- [ ] При precision ≥ 0.7 recall ≥ 0.8 (сейчас recall при precision 0.7 ≈ 0; порог ML рассинхронизирован с новым окном детекции)
- [x] Медианный lead time ≥ 48 ч до `incident_detected_by_operator` (206 ч)
- [x] Обучение + инференс на 1000 траекторий ≤ 5 минут на ноутбуке (без GPU) — полный пайплайн 2 мин на VPS (2 CPU)
- [x] Автотест на отсутствие утечки: переобучение на данных со случайно перемешанным таргетом даёт AUC ≈ 0.5
- [ ] Сводная таблица: физическая модель vs LogReg vs бустинг (частично: есть physics + ml_best, LogReg отдельной строкой нет)

## Этап 4. Бенчмарк «раньше оператора»

**Цель:** главный продающий артефакт — измеримое опережение типового оператора.

Задачи:

- [x] `[P0]` 4.1. Модель оператора: тревога при T зерна выше фиксированного порога (как на практике: 2 проверки в день по показаниям термоштанг) — порог 32 °C в разметке синтетики
- [x] `[P0]` 4.2. Метрика опережения: lead time нашей системы vs оператор по каждому инциденту (окно детекции `[start−72 ч; operator_detect]`)
- [x] `[P0]` 4.3. Отчёт `reports/benchmark.md`: распределение lead time, доля инцидентов, пойманных раньше оператора, цена ложных тревог

Критерии приёмки:

- [x] Медианное опережение оператора ≥ 24 ч на синтетике — 141 ч
- [x] ≥ 80 % инцидентов обнаружены раньше оператора — 100 %
- [x] FP-rate ≤ 2/силосо-месяц на рабочем пороге (уровень согласован с будущим пилотом) — 0.25
- [ ] График: 5+ примеров инцидентов с точками срабатывания системы, оператора и фактическим началом порчи

## Зависимости между этапами

```
Этап 0 → Этап 1 → Этап 2 ─┐
        └──────→ Этап 3 ─┴→ Этап 4 → Этап 6
                     └────→ Этап 5 → Этап 7 → Этап 8
```

- Этапы 2 и 3 можно вести параллельно после Этапа 1
- Этап 5 можно начинать параллельно с Этапами 2–4 (data contract не зависит от моделей)
- Этап 7 — единственный этап, требующий внешних договорённостей; начинать переговоры сразу после Этапа 1
